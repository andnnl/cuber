# Windows 桌面版首次连接自动获取蓝牙 MAC：设计规格

## 目标与现状

Windows 桌面版第一次连接 GAN／MG 魔方时，用户点击「连接魔方」、在设备选择框选中魔方，即可继续连接，不必先抄写 MAC。现有 Web Bluetooth 选择事件只提供不透明设备 ID 和名称；网页侧在设备选择后等待 `watchAdvertisements` 取 MAC，用户实测该路径未完成，而手动填写 MAC 可以连接。MAC 是当前 GAN 协议解密所需数据，不可将 Electron 的设备 ID 当成 MAC。

不改变 Android 与普通浏览器的连接流程；现有手填 MAC 继续作为自动识别失败时的明确兜底。本任务不重写现有 Web Bluetooth GATT 传输和 GAN 协议。

## 选型

- 推荐：Windows 原生 BLE 广播辅助扫描获取地址，现有 Web Bluetooth 负责设备授权和 GATT 通信。原生广播帧包含 48 位 `BluetoothAddress`，通过广播名称与选择的设备交叉核对。
- 仅缓存第一次手填的 MAC：后续体验好，但不满足首次免输入。
- 全面改为 Windows 原生 GATT：可以整合扫描和连接，但会重写通信协议边界，超出此次范围。

## 数据流与边界

1. Windows Electron 主进程打开选择框时，启动随包提供的受限扫描辅助程序。辅助程序调用 Windows Runtime 的 `BluetoothLEAdvertisementWatcher`，在有限窗口内输出扫描到的设备名称和 MAC；主进程只接受规范的 12 位十六进制地址、非空名称和当前轮次结果。关闭选择框、超时、退出应用时停止扫描，不留后台常驻进程。
2. 选择框中选中某个 Electron `deviceId` 后，主进程比较该条目的设备名称与扫描结果。仅有一个完全同名且地址唯一的广播结果时，将 MAC 暂存给本次设备选择；多个同名广播地址、缺失名称／广播或超时均视为不确定，不猜测。
3. 主窗口通过隔离的 preload IPC 查询「本次选中的 `deviceId` 对应的 MAC」，WebBluetoothTransport 在 `requestDevice` 返回后使用它，优先级为用户本次手填 MAC > 已与同一 Web Bluetooth 设备 ID 验证过的本地记录 > 本次唯一匹配的原生广播 MAC > 现有 `watchAdvertisements`。连接成功后才保存 `device.id → MAC` 的记录，避免错误候选污染下次连接；用户输入和保存的 MAC 都通过现有归一化与协议验证。
4. 若自动获取失败，连接面板显示明确错误及「用 MAC 连接」入口；不得一直停留「正在连接」。不要自动选择另一个同名设备、跨设备复用地址，也不要在日志中泄露不必要的设备标识。

## 构建与验证

- Windows 构建在原生 Windows runner 编译扫描辅助程序，并打入 Windows 安装包；Linux 构建不依赖 Windows SDK，Android 打包不包含辅助程序。构建失败时不得静默发布缺辅助程序的 Windows 包。
- 单元测试覆盖唯一名称匹配、同名多设备拒绝、不合法地址、手动输入优先、设备 ID 缓存隔离、选择取消与扫描退出；桌面回归确认 IPC 仅由受信任主窗口调用、失败可回退手动输入。
- Windows CI 校验辅助程序编译、资源进入安装包；真实首次连接需要 Windows + 实体魔方验收：首次无 MAC 点击设备后连接、转动同步、重启后同一设备复连、同名设备冲突与超时回退。

## 风险和限制

部分魔方广播名称可能缺失或与系统选择框名称不同，或 Windows 同时扫描受蓝牙适配器驱动限制；此时明确失败并保留手填，不冒险猜地址。无法在没有实体 Windows 蓝牙设备的 CI 环境中证明无线连接成功，CI 只覆盖扫描程序编译、纯逻辑和打包边界。
