# v1.0.13 离线分卷与双平台发布设计

## 目标与边界

发布当前 `master` 的 v1.0.13，不改动应用功能。GitHub 提供完整 Android APK、Windows 安装包和 Linux AppImage；Gitee 提供 Android APK，以及 Windows、Linux 安装包各自的分卷和双击解包入口。用户不需要安装 7-Zip，也不需要输入合包命令。

桌面安装包已经压缩，分卷直接切分原文件字节，不再叠加低收益的压缩层。版本提交为 `4924f97`，发布标签均为 `v1.0.13`。不覆盖或删除已有 Release。

## 附件格式

每个桌面安装包按固定顺序切成至多 90 MiB 的 `.part00`、`.part01` 等文件，最后一卷按实际剩余大小。入口文件与对应分卷放在同一个目录：

| 平台 | 分卷例子 | 双击入口 | 还原结果 |
| --- | --- | --- | --- |
| Windows | `Cuber-1.0.13-win-x64.exe.part00` | `Cuber-1.0.13-win-x64-unpack.exe` | `Cuber-1.0.13-win-x64.exe` |
| Linux | `Cuber-1.0.13-linux-x86_64.AppImage.part00` | `Cuber-1.0.13-linux-x86_64-unpack` | `Cuber-1.0.13-linux-x86_64.AppImage` |

入口为本项目构建的独立原生程序；Windows 使用 Win32，Linux 使用静态链接的 x86_64 程序。安装包的名称、分卷数量、每卷长度、完整文件长度和 SHA-256 在构建时固定进入口，不接受外部传入路径。Linux 下载后可能需在文件管理器首次开启「允许作为程序执行」，之后双击；还原的 AppImage 也可能需要同样的图形界面授权。Windows 未签名程序可能触发 SmartScreen 提示，发布说明如实告知。

## 解包流程与错误处理

入口从自身所在目录按序读取全部分卷，逐卷检查文件大小，并流式写入同目录的独占临时文件。计算还原文件的 SHA-256；只有长度与哈希均匹配，才以不覆盖同名文件的方式将临时文件改名为最终安装包。已有同名文件若哈希相同，显示「已解包」；若不同，则拒绝覆盖并提示用户处理。缺卷、截断、哈希不匹配、无写入权限和磁盘不足都要给出可见错误，不能留下冒充完整安装包的文件。失败时只清理本次创建的临时文件；不修改或删除用户已有文件。

Windows 通过原生对话框告知成功或错误，并提供最终文件所在位置。Linux 优先使用桌面通知或图形提示；即使桌面通知工具不可用，也要写入与入口同目录的结果说明文件，不能依赖用户阅读终端输出。入口只还原安装包，不自动运行安装程序。

## 构建、验证与发布

保留可重复执行的本地打包命令：读取现有 APK、AppImage 和 Windows 安装包，生成两平台分卷与入口，在发布目录输出 SHA-256 清单。构建不覆盖已存在且内容不同的发布附件。

用小型伪安装包先验证顺序、缺卷、损坏、同名文件保护和重复双击，再对真实安装包执行解包，与原件逐字节比对 SHA-256。Windows 入口至少使用 Wine 验证完整流程及错误提示，并核对 Windows 包内是当前 BLE 辅助程序。Linux 入口在本机以图形双击和首次授权流程验证。测试通过后创建两个远端的同名标签与 Release，上传对应附件，再读取远端资产清单核对名称、数量与大小；任何平台上传失败，应报告实际成功范围，不宣称两边都发布成功。

## 不做的事

不要求用户安装 7-Zip；不把分卷脚本放进安装器；不修改现有应用数据；不将大体积分卷加入 Git；不创建新的应用版本号；不自动运行解包后的安装包。
